1. Asynchronous code I don't see much of an issue with in Javascript, so it's more difficult for me to point out issues with it - but I'll try. I know there are isues with try/catch blocks, and error handling can be decently complicated with async/await. If a project were to get large or use a lot of async/await, setTimeout/Interval and the like, I could easily see error handling being a major time commitment when developing larger JS-based projects. Additionally, since typically most programmers are used to writing synchronous code with asynchronous pieces, I could also see why it might be difficult for people who don't usually work with fully-async environments to work with having many functions run at the same time and modifying things.

2. I would think they made it loosely typed to make it easier to develop with - a lot of 90s/2000s languages had this feature, take C++ adding `auto` or Lua having the same loose typing from the same era. Computers were powerful enough to handle it, and it's supposed to make life easier for developers, so I could see why it would be a reasonable add. Notably, a lot of web developers were (and still are) not programmers - they write a block and want their text to move around so they add some Javascript to it. On the topic of async/await, it's only natural in a web environment - sometimes a function needs to wait on a web request, and we don't want that blocking off the entire program. If we implement that in one place, then it's reasonable to allow, not force, the application of async/await everywhere. Additionally, by making the whole runtime multithreaded per-function, it's makes handling things like event handlers, animations, dynamic content loading, etc. significantly easier than having the developer juggle a content scheduler.

3. Compiled languages first are passed through a compiler, which turns the high-level code into something else - typically machine code, but nowadays WebAssembly or compilation of strictly typed supersets of Javascript like Typescript to Javascript are widespread. Interpreters are rather a runtime code, well, interpreter, that directly reads in the uncompiled code as text and determines the actions to take. Javascript is an interesting combination - it is interpreted, *but* also compiled. The interpreter determines what to do with a function, then when called passes it to a compiler which turns it into machine code for performance reasons. This is a JIT compiler, which I know of from things such as emulators and LuaJIT. This means that JS is modifiable at runtime, and significantly easier to debug - as we have seen. We can set breakpoints at the exact line via text without any external tools, see the complete source code (not a decompilation) of unminified JS, and even make custom userscripts which modify the behavior of known website code. The drawback is that you have to account for this - someone can very easily manipulate your verification code for SQL to simply pass you a string and now you've had your database dropped because Little Bobby Tables thought it would be funny. Also, this means that you have to optimize your code for pre-compiled size as well as speed. Typically websites just minify their JS, which is typically fine, but a lot - even some big ones - don't.

4. Because frameworks create dependencies and complexity. Frameworks are all different, the best framework seems to be a concept which differs from hour to hour, and you always run the risk of a breaking change in the library being made and soon after a critical security update. Vanilla Javascript stays mostly the same - a lot of Javascript code that ran back in the 90s when it first got popular still runs today on modern browsers without too much hassle. Javascript is standardized, regulated, has a committee, has dedicated support for backwards compatibility - a lot of frameworks don't have that. Javascript will likely last on, despite its complexity in large codebases, regardless of framework. And that's the thing - vanilla JS will carry over to any framework you choose. Choosing a framework typically doesn't remove any features of vanilla JS, at least not that I know of (I haven't used any frameworks, to be clear), so knowing how vanilla JS works, and how to avoid the common quirks people like to riff on, will carry over to any framework you may later choose. Mastery of the foundation means even a house of cards will only fall in an earthquake.

5. It completely relates to the project. We're planning on making a card game, and practically the entire game will be written in vanilla Javascript. The layout and styles, of course, will be in HTML - but the game logic, card movement, hand handling, deck dealing, mouse interaction, UI updating, and so much more will have to be taken care of in Javascript simply because HTML and CSS don't offer the features we need out of them. Knowing how to use JS, and use it *well*, means we can build something that will stand up as we build on top of it.

    Now. To add, I do enjoy Typescript, it's not a framework, but it solves most of the odd type confusion that happens when you try to do operations on numbers. But still, Typescript is just Javascript with types - everything but the typelessness will still remain. JS will JS, no matter the icing on top. It's still worth knowing what you're doing in vanilla JS so you can work with it and understand the code.
